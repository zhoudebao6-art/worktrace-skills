# 微信数据库证据通道

v0.6.0 增加可选的微信数据库读取通道，用于保存员工已授权工作账号中的消息，再供个人复盘和总控分析。采集不调用语言模型，不打开会话、不抢焦点、不发送消息，也不改变已读状态。它和现有 UIA、应用活动、资料版本采集互补；安装新版本不会自动开启数据库通道。

本机可能只是员工分控。无总控、不同局域网或总控暂未上线时，继续本地保存与离线移交，不创建假总控，不重新登记员工。已有采集的身份、工作时段、应用范围、文件策略、学习强度和暂停状态均沿用。

## 先确认支持，再启用

只有目标员工电脑上的实际探测与验收能证明该电脑可用。当前适配器面向包含 `db_storage/message` 的 Windows 微信 4.x 账号目录，不能据此承诺所有 4.x 版本都兼容。微信版本、数据库结构、账号目录、密钥准备或权限不满足时，明确返回不可用或待处理；保留原 UIA/文件采集。不能拿开发机合成数据库测试、解析器存在或进程启动成功当作员工微信已兼容。

1. 先用 [v0.6.0 原路径升级](upgrade-v0.6.0.md) 更新实际运行引擎和三个分控技能。正在工作的员工可继续使用软件完成下载和预检；维护时有一段正常停机、冷备和重启间隔，并非零停机升级。
2. 核对本机唯一部署与员工账号。只检查明确的账号目录和已登录账号；发现多个账号时要求选择 `AccountRoot` / `AccountId`，不拼接多个账号，不遍历其他员工目录。员工账号标识不同于 WorkTrace 的员工编号，两者都要保留。
3. 运行新包中的 `scripts/Configure-Wechat.ps1` 准备只读解析器和明确来源。解析器只使用 `runtime/wechat-reader-release.json` 固定的发布资产及校验值；不得下载来历不明的“全量导出工具”。初次密钥准备会涉及本人已登录微信的进程读取，安排在员工已同意的空闲时机。普通安装和升级不主动做此步骤；需要时显式加 `-PrepareKeysWhenIdle`，脚本要求至少 120 秒无键鼠活动及唯一已运行的微信进程，不满足时明确延期，不自动等待后重试。不注入微信进程、不关闭微信，也不把密钥打印到对话、提交 GitHub 或放进个人总结。
4. 在数据库通道仍关闭的情况下调用 `wechat-probe`。这是元数据兼容性检查，不导入正文，不表示已完成消息采集或性能验收。失败时保留具体原因；不反复准备密钥或转为全盘扫描。
5. 明确消息起点和排除会话，保存完整策略；启用后仍受全局记录开关与工作时段约束。通过员工确认的测试会话核对私聊、群聊、发送人、收发方向、重复与补漏，再观察实际应用响应。此前暂停则保留暂停；不为了测试擅自恢复记录。

示例中的路径必须替换为目标电脑的原部署、解析器目录和已确认账号，不能引用开发电脑路径：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Configure-Wechat.ps1 -DeploymentRoot 'D:\WorkTraceNode' -ReaderDirectory 'D:\WorkTraceReader' -AccountRoot 'D:\本人微信工作账号目录' -AccountId '已确认账号ID'
& 'D:\WorkTraceNode\runtime\node.exe' 'D:\WorkTraceNode\src\admin-cli.mjs' --command wechat-probe --role collector --dir 'D:\WorkTraceNode\data'
& 'D:\WorkTraceNode\runtime\node.exe' 'D:\WorkTraceNode\src\admin-cli.mjs' --command wechat-status --role collector --dir 'D:\WorkTraceNode\data'
```

`ReaderDirectory` 可以省略，由配置脚本准备固定发布解析器。实际解析器/微信版本不支持时不要填写虚假成功结果。`AccountRoot` 和 `AccountId` 可由脚本识别唯一明确来源；多账号或识别不确定时必须明确指定。

来源配置保存在原 `data/wechat-source.json`，只记录路径和账号标识；解析器密钥 profile 单独保存在原运行目录的 `private` 下，不写入工作证据数据库或离线移交包。它是原员工机器的私有运行材料，不是可公开的调试信息。完整运行目录冷备仍需保护该私有材料。

配置与 profile 的明文账号 ID、规范化账号目录必须一致；不符时拒绝读取，不能用另一账号的 profile 试探。Node 侧仅检查格式和绑定，不解密或输出 DPAPI 密钥材料。

启用策略文件只保存在本机，下面是字段说明，不应照抄示例时间启用历史回溯：

```json
{
  "enabled": true,
  "interval_seconds": 30,
  "max_ms": 1500,
  "max_rows": 150,
  "capture_since": "2026-10-15T09:00:00.000Z",
  "excluded_conversations": []
}
```

将 `capture_since` 设置为本次实际授权启用时刻的 UTC 时间；核对排除会话后，再用 `src/admin-cli.mjs --command wechat-configure --role collector --dir <原data> --input <本机policy.json>` 提交。默认不导入启用前或工作时段外的消息。原全局记录关闭时，数据库策略启用也不应开始采集；工作时间外休眠。排除名单为空只表示该已确认账号内没有额外会话排除，不能扩展到其他账号。

`Configure-Wechat.ps1 -Enable` 是可选快捷启用：必须先核对范围，它在探测成功后使用当前策略，首次来源将消息起点设为当时 UTC 时间；全局采集开关仍不变。需要排除特定会话时先按完整策略流程配置，不省略范围核对。该开关不代表测试消息、准确归属或性能已验收。

## 记录的含义

| 字段或来源 | 能说明什么 | 不能据此推断什么 |
|---|---|---|
| 账号、数据库代次、分片/表、源消息编号 | 消息来源与增量去重边界 | 其他账号或另一台设备的消息已合并完整 |
| 会话 ID、会话类型、实际发送人 ID | 区分私聊、群聊和群成员；同名联系人不混用 | 备注名/昵称相同就是同一个客户；群 ID 就是发言人 |
| `identity_status=unknown` | 无法可靠归属；发送人和方向保留未知 | 通过气泡位置、称呼或上下文猜人 |
| 本账号发出的记录 | 本账号具有一条发出方向的数据库记录 | 一定是本员工手打、对方已读、已同意或业务办结 |
| 原始消息与修订链 | 观察到的正文、撤回/变化和各次来源摘要 | 数据库已删除的内容一定能还原 |
| UIA / OCR / 文件证据 | 可见界面、应用活动与另行保存的原件 | 一条消息一定对应某次点击；打开文件等于完成审查 |

`chat.message` 使用事件协议 1.3；消息标识使用十进制字符串，不能转成可能失真的 JavaScript 大整数。正文、稳定身份、来源和修订应保持关联。个人复盘按同账号、同会话理解来往，显式区分原始观察、模型推断和人工声明；不同客户的片段不能串成一次完整接待。

本版将撤回提示等非文本内容保留为原始系统/XML 内容和解析缺口，不会执行其中的外部引用，也不会自动认定某条历史消息已撤回。`message_status` 不能代替对撤回目标的核验；实际观察到同一来源正文变化时才建立该来源消息的修订。

相同账号、会话与非零 `server_message_id` 可用于识别跨分片或重建代次的同一消息；查询提供派生的 `logical_message_id`。物理来源 `source_message_key`、修订及原证据仍分别保留，不自动合并。缺少服务器 ID 时不按相同文本猜测重复；会话统计是物理来源记录数，不能直接当唯一消息数或员工回复次数。

本版媒体字段记录类型、引用与缺口，不等于已经采集图片、语音、视频或文件的原件；`not_collected`、`unavailable`、`unsupported` 必须保留。没有实际获取和核对的图片不得称已看懂，没有音频与转写不得称已听懂。化工结构式、公式、数值、单位与修订仍需要资料原件取证，不能靠微信文本补写。

## 增量补漏与性能

读取采用独立原生只读进程和有界分页，限制轮询频率、行数与时间；新消息、重叠复查和历史核对各自留检查点。页提交和游标推进需要一致，崩溃重试不得重复制造消息；检测到来源代次或账号变化时应明确处理，不能拿旧游标跳过新库。

补漏范围只限于已授权范围内、微信确实写入本机且仍可读取的记录。它不保证云端全部历史、其他设备未同步消息、已经物理删除的内容或未下载媒体。最新消息时间很早不一定是故障，应结合最近成功读取、待处理数量和覆盖缺口判断。

不得为“提速”周期性全库复制/解密、重建微信索引、写入原数据库、执行源库检查点/修复，或把正在变化的数据库伪装成不可变文件。低负荷是设计和预算约束，仍须实测员工电脑：对相同应用和操作比较启用前后响应、读取字节、CPU/内存与积压。WorkTrace 自身 CPU 低不能单独证明微信不卡。发现卡顿优先定位读取轮次/超时与 UIA 重复负担，不静默减少工作范围、降低模型或关闭原采集冒充优化。

## 读取、学习和移交

重连原 WorkTrace MCP 即可使用新增的三个只读工具，不需要再注册一套相同工具：`wechat_status` 查看状态，`wechat_list_chats` 看已收集会话，`wechat_read_chat` 必须同时指定 `account_id` 与 `conversation_id`。它们从 WorkTrace 已保存证据查询。原部署 `src/wechat-mcp.mjs --data <原data>` 是可选独立入口，只有确实需要独立连接时使用。不要将其与旧的微信发送 MCP 混为一体；原发送能力保留独立，升级不启动发送或自动回复。

聊天查询每条正文最多返回 6000 个 UTF-16 字符单位，单页条目 JSON 总量不超过 100000 个单位；`text_truncated` 和 `text_omitted_characters` 明确截断。按 `next_before` 继续翻页，不能把首屏当全部上下文。原文仍在原始事件内，确需核对时使用有界的证据读取工具；个人学习对嵌套正文和外层正文使用同一预算。

采集不消耗模型调用额度。个人学习继续使用已配置的 `gpt-6.1-sol` 与原 `high`/`xhigh`，只有学习执行器或手动复盘才调用模型。总结引用原始事件，标明未知发送人、缺失媒体、会话上下文截断和未覆盖消息；不能因为记录数量增加就称已经学会接待。

总控接收这些消息前也必须支持 v0.6.0 / 协议 1.3。旧总控拒绝时本地队列保留并报告版本问题，不删除失败消息、不降级伪装成旧 UIA 事件，也不由员工电脑擅自改总控。离线仍按原完整移交流程导出，消息修订和证据引用随记录核验；解析器密钥与访问能力只用于原员工机器，不能作为业务证据随包传播。导入数量不证明已形成个人方法，总控仍要核对个人总结和缺口。

## 员工电脑验收记录

至少记录：实际微信/解析器版本、明确账号及范围、探测结果、实际入库与消息归属、暂停/时段/排除会话结果、重启后增量去重、媒体与历史缺口、员工应用响应、旧采集状态，以及是否已由兼容总控接收。无现场条件就写“通道未启用、待员工电脑验收”，保留原采集；不可改写为“全部微信消息已完整采集”。
