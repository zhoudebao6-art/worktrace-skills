# v0.5.2 架构复查与优化报告

复查日期：2026-10-14。主要场景是员工电脑独立记录数日、与未来总控不在同一局域网，之后移交工作证据；同时检查联网分控与其他岗位的复用边界。本报告描述源码与合成验证，不代表已在所有员工电脑升级或已证明可以独立完成业务。

## 结构判断

本地服务负责可见取证、数据保存和有界队列；Codex 按证据批次总结；个人原始证据和总结再汇入明确指定的总控。这种分层适合当前目标，暂不需要把整个桌面交给持续视觉模型，也不能只靠 Skill 文本承担后台服务。需要修正的是学习覆盖、异常恢复和部署状态的衔接，而非更换整套基础架构。

统一数据库统一事件结构、身份和来源，不是让所有电脑共写一个网络 SQLite 文件。离线分控本地采集与学习不依赖总控在线；总控未上线时保留证据与总结，通过经过核验的加密移交接纳。离线设备没有双向命令通道，联网后才有受限任务与回执。

本版合入远端已有的 LAN 链接接入、私有邀请码和 Connect 连接恢复，保留它们的身份、证书和原状态约束。角色模型继续固定总控 Astra、分控 6.1 Sol；新部署默认 xhigh，已有合法 high/xhigh 保持，显式变更才调整。这样既不把已有 high 部署静默提高费用，也不把已有 xhigh 部署降级。连接恢复与引擎升级分别验收。

## 已确认的问题与处理

| 问题与可复现条件 | 本次处理 | 仍保留的边界 |
|---|---|---|
| 大量带标题的无正文活动占据个人批次，较后的正文长时间没有进入学习 | 最早 1000 条待处理窗口内，正文、文件、业务事件优先；同小时/进程/采集状态/完整标题的元数据归组，未选记录保留 | 不跨过窗口全库找正文；不同标题不得归并。大量积压仍需多批 |
| 只见“日报”容易误认为当天所有工作已被学习 | 日报注明总结保存日、原始证据日期范围、代表/上下文计数、领取时的扫描与未选数量；手动保存后也尝试重建 | 报告是派生视图；模型结论和有来源的假设仍需核验 |
| 原始证据移交成功，但没有 learning.summary，默认总控学习得不到个人方法 | readiness 明确提示缺口；优先原机补总结，原机不可用时总控暂停自动后 source=all 手动审阅 | 不冒充员工补造个人总结；纯原始证据不会自动生成个人候选 |
| 文档建议把 states、wait_for 等写入 loop，但严格 API 会拒绝 | 文档严格列出 loop-draft/1.0 的现有字段；额外状态图和执行设计放单独附录 | 本版保存候选草稿，不是通用状态机执行器 |
| 候选草稿来自原个人方法，可能被误认为已吸收总控纠错 | 要求先核对总控 analysis，再显式 revise，记录新版与留出案例 | 自动 derive 不会自行完成跨员工规则治理、业务授权或发布 |
| 下行第一页都是未来任务，后来的即时消息无法及时取得 | 每设备持久分页轮转，保留确认与取消回执重投 | 收到消息不是已经回复或获准执行消息中的任意指令 |
| 总控失败检查点重复挡住其他批次 | 每批本地日最多一次自动尝试，未尝试批次优先，失败保留检查点 | 总控每天预算共享；不是员工间严格公平分配，也不保证当夜全部完成 |
| 修改设置或离开允许时段后，迟到模型结果仍可能保存 | 实际配置变化、窗口结束和停机撤销旧执行有效性，已预留用量保留 | 取消不能追回已发生的模型调用；离线失败仍需显式重试 |
| 重复服务、停机未结束就复制或替换目录，会造成运行与磁盘状态不一致 | 同数据目录/同机活动身份互斥，后台任务排空后停机；升级先冷备，再更新引擎与技能并重连 MCP | 无法发现另一台不联网机器的活动克隆；仍只保留一个活动来源 |
| 两个首次安装请求同时绑定、同步请求等待正文期间设备被撤销、坏回执使同包部分数据提前提交 | 首次绑定竞态受控；同步完成读取后重新核对授权，事件/策略/回执按整包事务处理，失败回滚 | 已撤销设备不能借在途请求继续写入，失败包保留原端待传状态 |
| 首次分控/总控配置写盘失败，遗留登记或已开启监听而无法安全重试 | 失败回滚本次登记，关闭本次新建总控监听，保留明确错误并允许修复原因后重试 | 不把配置写盘失败报告为部署成功，不删除用户已有证据 |
| 把加密完整包等同于可安全恢复，忽略内部引用或本地检查点损坏 | 完整移交增加事件、原件、引用和恢复状态检查 | 加密/结构校验不证明记录语义、作者归属推测或业务结果正确 |

## 学习覆盖的合成验收

固定输入为 450 条同小时、同应用、同状态、同完整标题的无正文活动，随后一条含正文记录。旧选样三批各 50 条后仍有 301 条未处理，正文尚未进入批次。新版以 limit=2 领取，先给出正文和一个元数据代表，同时记录 450 条归组成员，合计覆盖此次领取的 451 条新事件。原始 event_id、hash 与 JSON 逐条不变。

这个结果验证的是取样和来源保存，没有证明模型理解了正文，也没有把 451 条记录换算成工时。另有回归验证 A/B/A 标题不会被合成一个组、第 1001 条正文不被越界消费、旧批次没有 selection 元数据仍可恢复、未解析原件及结构化任务优先、未选记录继续待处理、日报区分原始日期和保存日期。

本轮学习改动在合并远端接入功能前的定向回归为 **22/22 通过**，使用固定 Node v22.23.2、Windows、本地隔离 SQLite、合成身份和证据；未采集实际桌面，未发送客户消息，未调用真实模型。复现命令（先将 TEMP/TMP/TMPDIR 指向指定缓存盘）：

```powershell
& .\runtime\node.exe --test tests/learning-coverage.test.mjs tests/optimization.test.mjs tests/offline-worker.test.mjs tests/performance.test.mjs
```

队列/窗口恢复、运行锁/停机、readiness、同步与移交完整性分别由 `loop-resilience`、`runtime-lifecycle`、`readiness`、`sync-integrity`、`handoff-integrity` 测试覆盖。这些早期定向结果不累加为新的测试数量；最终联合验证见下节。

合并后的定向验证另有 `runtime-lifecycle` **9/9** 与合并核心回归 **45/45** 通过；`sync-integrity` 包含四项同步/首次绑定事务场景。这些定向用例也包含在下述联合全套中，不代表员工现场验收。

## 另一台 Codex 应如何使用

1. 先查已安装技能的 deployment.json、实际服务版本与运行路径。明确 collector/hub、offline/联网、本机是否已有活动服务；阅读源码不代表本机就是总控。
2. 排障先按需执行 readiness，分别查记录、正文/原件、总结、队列、预算和磁盘。旧服务缺少新接口时按升级说明处理，不依据技能文字虚构运行能力。
3. 化工等需要原件的岗位，先按事件导出保存版本并核对公式/结构式/表格。自动 worker 只收到有限文本和图像，不会自行调用文件工具；没有对应读取能力就标记缺口。
4. 复盘保留 observed/inferred/unknown 与逐条来源。个人总结先回答怎么做、如何判断、怎样检查、何时不适用；总控再比较和修订，不把个人习惯直接升为公司规则。
5. 数日后移交先核对包与身份，区分“仅原始证据”和“含个人总结”。原机不可用时采用明确的总控人工复盘路线，不补造原员工模型输出。
6. 已有部署按[更新清单与升级步骤](upgrade-v0.5.2.md)更新完整受管引擎、对应技能、版本绑定，并重连本 WorkTrace MCP；保留原数据、身份、模式、配置与暂停状态。只更新技能不能宣称运行服务已升级。

操作细节见[整体架构](architecture.md)、[数据与运行边界](data-and-operations.md)、[总控候选规则](../skills/worktrace-hub/references/candidate.md)。采集、总结、候选和执行各有独立验收，当前结构化业务任务只支持客服跟进和初稿质检；其他岗位可以复用证据层，但业务执行器与独立办结验证仍需另做。

## 发布与现场验收边界

仓库只发布通用代码、技能与合成验证。实际采集范围、Word/WPS/微信可访问性、化工原件读取质量、员工习惯复原准确度和业务独立完成率，必须由目标电脑及真实留出案例验证。公开仓库不应包含真实原件、总结、数据库、姓名清单、登录或登记凭据。

本地数据库、原件和模型调试记录仍会增长；当前没有自动保留期限或全公司模型并发管理。总控需要明确容量、备份与费用政策，并按试点失败原因决定补业务接口、加强原件阅读还是调整流程，而不是靠提高采样频率或降低模型质量掩盖证据缺口。
