# v0.6.0 微信增量证据与原路径升级验收

日期：2026-10-15。目标是减少员工工作期间的界面轮询，在保留原采集与离线分控的基础上增加微信数据库证据。开发电脑不是公司总控，也没有以真实微信、员工账号或客户消息进行测试。

## 架构与复用范围

```text
员工本人工作微信的本机数据库 / WAL
  → Windows 原生只读解析器（加密页、短读取事务、低优先级）
  → 有预算的增量读取（新消息 / 重叠核查 / 历史核查）
  → WorkTrace 本机数据库（消息与游标原子提交、修订链）
  → 既有 WorkTrace MCP 中的微信只读工具
  → 个人复盘、证据引用 → 局域网同步或离线移交
```

沿用之前微信 MCP 的 JSONL 工具调用方式与 `wechat_status`、`wechat_list_chats`、`wechat_read_chat` 三个查询工具名称。新工具查询已保存的 WorkTrace 证据；旧 MCP 的界面控制与发送功能保持独立。新增采集不通过切换会话、截图或点击头像识别发送人，不启动旧后台自动接待。

使用 Tencent WCDB 固定版本内的 SQLCipher 核心和 Windows CNG，公开源代码、固定依赖下载摘要和许可证。发布包提供预编译解析器，员工电脑不需要安装编译环境。首次访问材料准备只在明确工作账号、同一 Windows 用户、员工空闲时进行，使用只读进程访问，不注入或修改微信；后续轮询不反复扫描进程。访问材料由 DPAPI 保护，留在原电脑的 `private` 目录，不进入业务移交包。

## 消息完整性与归属

- 账号、数据库代次、分片、表和实际 rowid 共同约束检查点；64 位消息编号保留字符串。新消息、重叠复查与有界历史核查各自推进，重启后恢复，不按相同正文去重。
- 只有完整、来源一致且未取消的结果才能提交；页内消息与游标同一事务落库。源库繁忙、分页失败、代次变化或回退时保留原检查点并报告。
- 会话由结构化账号映射识别，群会话与实际群成员分别保存；无法可靠解析时保留 unknown。发出方向只能证明本账号存在发出记录，不能证明某员工手打、对方已读或业务完成。
- 观察到正文变化时追加修订，保留原始证据与修订引用。压缩截断、超大内容、未知编码、缺失媒体明确记录缺口，不把解码失败解释为空消息。
- 查询按账号和会话隔离，输出有条数与正文预算。跨来源重复保留来源证据，个人复盘不得把相同服务端消息的多份观察当多次业务沟通。

## 性能与运行边界

默认 30 秒间隔、每轮 150 行和 1500 毫秒读取预算；目录与映射缓存、常驻隐藏解析器、短只读事务、错误退避共同限制开销。采集不调用模型。首次目录发现、磁盘竞争和进程调度仍可能超出单个查询预算，不能把预算称为目标电脑绝不卡顿的保证。

数据库读取受原全局记录开关、工作时段、启用起点及会话排除共同约束。暂停后拒绝在途结果，不补采暂停区间。原 UIA/文件采集保持原配置；新增通道失败不关闭原采集。没有数据不等于已经完整覆盖，应查看最近成功读取、检查点、错误与缺口。

## 已验证的范围

验证使用隔离 SQLite 数据、合成员工身份和自建测试进程，临时文件位于 `D:\codex+`。没有操作真实微信桌面、发送消息或调用真实模型。

- Windows PowerShell 5.1 可构建固定依赖的生产解析器。实际生产二进制 9 项测试通过，无跳过：独立校验加密页、读取已提交 WAL、排除未提交事务、分页与 64 位编号、DPAPI、来源/查询拒绝，以及仅自建进程的准备与活动中止。测试前后源 DB 与 WAL 摘要一致。
- 跨层测试实际经过加密 DB/WAL、原生常驻解析器、JS 提供器、增量引擎、WorkTrace Store 与查询工具，覆盖发送人映射、新记录追加、过大响应拒绝且不推进游标。原生进程低优先级且能退出。
- 存储、协议、API/MCP、个人学习证据与加密离线移交测试覆盖：事务回滚、去重、修订链、身份隔离、工作时段/暂停、取消后的迟到结果，以及总控重建消息查询索引但不导入源读取检查点或私有密钥。
- 升级测试分别检查运行与停机分控、备份核验、目录与身份互斥、受管文件冲突拒绝、原证据和原件保留、原采集/学习状态恢复；新数据库通道不会因升级自动启用。

本机完整 Node 测试 277/277 通过、零跳过；随后新增的离线消息索引与游标完整性专项 28/28 通过，受影响的旧移交/完整性/微信集成 35/35 通过。Windows PowerShell 5.1 的总控加双分控隔离部署（跳过实际桌面采集）、独立离线部署、9 场景原路径升级和性能诊断验证均通过，测试服务均已退出。

配置链另用精确发布版解析器验证：已存在离线分控 → 原 profile → 配置脚本 → 元数据探测 → MCP stdio 查询。数据库来源开关启用后，全局采集与学习仍保持暂停，原身份/stream/profile 不变，零消息误入库；源 DB/WAL 摘要一致。该测试只使用自建数据库和 DPAPI 材料，不运行真实微信密钥扫描。

另用真实 v0.5.2 标签（commit `6a1dc22858c6073c6d3924c8c316b489650d4366`）的原嵌入引擎完成升级演练：预检、完整冷备、原路径替换、实际 v0.6.0 API 与 readiness 核验通过。6 条原事件 JSON/摘要、2 份文件原件、1 张证据图、个人总结与未完成批次，以及原身份、配置和 stream 保留；offline、high、采集暂停和学习暂停保持，微信新增通道仍默认关闭。最终引擎清单 SHA256 为 `56245509f2997182531206b86c484e0f6370792464998110967702cea79a7d00`，全部 81 个受管文件核验通过。

不同层次的测试不替代员工现场验收；GitHub CI 会从固定源码重新构建解析器并运行所有 Node 测试。

## 员工电脑仍须验收

适配范围是具有 `db_storage/message` 结构的 Windows 微信 4.x，尚未验证全部版本。员工机部署指令须先检查实际账号与结构，再探测、启用并核对正常授权消息。密钥不在进程内、权限不足或数据库结构变化时报告通道待支持，保留原采集，不反复尝试全库解密。

不能恢复未同步到本机、尚未落盘或已物理删除的记录；媒体目前保存类型、引用与缺口，不保证图片、音频、视频和附件原件已取得。默认只读取本次启用后的授权工作时段消息；历史核查不是不受范围限制的全量导出。源文件代次与高水位回退能识别常见替换，但同文件同表原地重建并复用 rowid 的所有情况仍无法保证发现。

现场需记录微信版本、实际账号、私聊与群成员归属、重启去重、暂停/时段/排除效果、积压和应用响应。需要总控接收协议 1.3 时，真实总控也应升级到兼容版本；尚无总控的分控继续离线保存和移交。

升级步骤见 [原路径升级手册](upgrade-v0.6.0.md)，员工电脑指令见 [固定版本升级指令](../prompts/upgrade-worktrace-v0.6.0.txt)。
